
## **0:25–0:35 — CSRF-защита (Cross-Site Request Forgery)**

---

### 🔹 **Цель блока:**

Научить студентов защищать веб-формы от CSRF-атак, объяснив механизм токенов, почему cookie недостаточно, и как фреймворки делают это автоматически.

---

### 🔸 **Что такое CSRF?**

**Определение:**

> CSRF — это атака, при которой злоумышленник заставляет браузер авторизованного пользователя отправить вредоносный запрос на доверенный сайт **без ведома пользователя**.

---

### 🔸 **Пример атаки без защиты:**

На сайте `bank.com` есть форма перевода денег:

```html
<form action="/transfer" method="POST">
    <input type="hidden" name="to" value="attacker">
    <input type="hidden" name="amount" value="1000">
    <input type="submit" value="Send money">
</form>
```

Пользователь залогинен и посещает вредоносный сайт с этим HTML. Браузер автоматически подставит **куки сессии** и отправит запрос → деньги переведены.

---

### 🔸 **Почему cookies недостаточно?**

Браузер **автоматически** прикладывает cookies ко всем запросам на домен, включая POST-запросы.  
⚠️ Это значит, что злоумышленник может использовать вашу авторизацию, **не зная логина/пароля**.

---

### 🔸 **Как защититься?**

#### ✅ **CSRF-токен:**

1. Сервер генерирует уникальный токен.
2. Вставляет его в каждую форму как скрытое поле:
```html
<input type="hidden" name="csrf_token" value="abc123">
```
3. При отправке формы — сверяет токен с тем, что хранится в сессии.

---

### 🔸 **Double Submit Cookie (альтернативный подход):**

1. Токен пишется в cookie `XSRF-TOKEN`.
2. JavaScript добавляет его в заголовок или тело формы.
3. Сервер сверяет значения из cookie и тела запроса.

Используется, например, в SPA-приложениях (Vue, React).

---

### 🔸 **CSRF в Laravel (Blade):**

Laravel **автоматически** защищает все POST/PUT/DELETE/… формы от CSRF.

#### ✅ В Blade:

```blade
<form method="POST" action="/profile">
    @csrf
    <input type="text" name="name">
</form>
```

`@csrf` генерирует скрытое поле с токеном:

```html
<input type="hidden" name="_token" value="qwerty123...">
```

Laravel сверяет этот токен при каждом запросе.  
Если не совпадает или отсутствует → **419 Page Expired** (ошибка CSRF).

---

### 🔸 **CSRF в Symfony (Twig):**

В контроллере:

```php
$csrfToken = $csrfTokenManager->getToken('delete_user');
```

В шаблоне:

```twig
<input type="hidden" name="_token" value="{{ csrf_token('delete_user') }}">
```

В контроллере на проверке:

```php
if (!$csrfTokenManager->isTokenValid(new CsrfToken('delete_user', $_POST['_token']))) {
    throw new InvalidCsrfTokenException();
}
```

---

### 🧪 **Интерактивная демонстрация:**

1. Покажите форму без `@csrf` → Laravel отклоняет запрос с 419.
2. Добавьте `@csrf` → запрос проходит успешно.
3. Удалите токен в DevTools → снова ошибка 419.

### ❗ Вопросы для обсуждения:

- Почему токен нельзя угадать?
- Что будет, если кто-то скопирует HTML формы и откроет на другом сайте?
- Чем CSRF отличается от XSS?
- Почему GET-запросы **не защищают CSRF** в Laravel по умолчанию?

---

### ❓ **Почему токен нельзя угадать?**

**Ответ:**  
CSRF-токен — это **криптографически случайная строка**, сгенерированная сервером.  
Он:
- уникален для каждой сессии (или даже формы),
- достаточно длинный (обычно 32+ байта),
- не передаётся в URL или куках.

**Злоумышленник не имеет доступа к токену**, так как:

- он находится либо в сессионной памяти сервера,
- либо в `input type="hidden"` формы, к которому нельзя получить доступ с другого сайта из-за Same-Origin Policy.

**Пример токена:**

```
XCSRF-TOKEN: e3f2c5697e944781a54f45fa8e5c1c79
```

---

### ❓ **Что будет, если кто-то скопирует HTML формы и откроет на другом сайте?**

**Ответ:**  
Если HTML-форма скопирована вручную и размещена на внешнем сайте, то:
- Вредоносный сайт сможет сымитировать внешний вид и структуру формы.
- Но **токен, встроенный в оригинальную форму**, не будет действителен на сервере.
- А сгенерировать новый действующий токен злоумышленник не может (у него нет доступа к сессии пользователя).

**Результат:** при отправке формы сервер **не найдёт** или **не сможет подтвердить** CSRF-токен → запрос будет отклонён (например, HTTP 419 в Laravel).

---

### ❓ **Чем CSRF отличается от XSS?**

|                    | **XSS** (Cross-Site Scripting)              | **SCRF** (Cross-Site Request Forgery)           |
| ------------------ | ------------------------------------------- | ----------------------------------------------- |
| Что делает         | Вставляет и выполняет вредоносный JS-код    | аставляет пользователя выполнить запрос         |
| Цель               | Выполнить JS в браузере жертвы              | Использовать авторизацию жертвы на другом сайте |
| Вектор атаки       | Через поля ввода, комментарии и т.п.        | Через внешние сайты, email, скрытые формы       |
| Требуется ли вход? | Нет, атакуют всех                           | Да, жертва должна быть авторизована             |
| Методы защиты      | Экранирование (`htmlspecialchars`, фильтры) | CSRF-токены, проверка Referer/Origin            |


---

### ❓ **Почему GET-запросы не защищают CSRF в Laravel по умолчанию?**

**Ответ:**  
Потому что **GET-запросы должны быть идемпотентными**, то есть **не изменять состояние сервера** (по стандарту HTTP). Примеры
- `GET /profile` — просто получить профиль
- `GET /logout` ❌ (плохо, должно быть POST)

Если разработчик всё делает правильно, то
- Только `POST`, `PUT`, `PATCH`, `DELETE` изменяют состояние,
- Значит **только они требуют CSRF-защиты**.

Laravel следует этому принципу:  
✅ CSRF-проверка включена только для **state-changing** запросов.  
❗Если вы используете `GET` для чего-то вроде удаления — это архитектурная ошибка.

Хочешь, подготовлю вопросник-миниквиз по этим темам для студентов?

Хороший вопрос — в этом примере **злоумышленник не модифицирует HTML на сайте `bank.com`**. Он создает **свой сайт**, на котором размещает **вредоносную форму**, которая отправляет **запрос на `bank.com`**, пользуясь тем, что браузер пользователя **автоматически подставит куки**, если пользователь в этот момент авторизован на `bank.com`.

---

### 🔹 Как выглядит атака CSRF **в реальности**

#### Сценарий:

1. Пользователь логинится в `bank.com`. У него появляется cookie сессии, например:

```
Cookie: session_id=abc123
```
   
2. Он **не выходит** из аккаунта и переходит на сайт злоумышленника `evil-site.com`.
3. На `evil-site.com` размещён такой HTML:

```html
<form action="https://bank.com/transfer" method="POST" style="display: none;">
  <input type="hidden" name="to" value="attacker">
  <input type="hidden" name="amount" value="10000">
  <input type="submit">
</form>
<script>
  document.forms[0].submit();
</script>
```

4. Когда браузер загрузит этот HTML, он **автоматически** отправит POST-запрос на `https://bank.com/transfer`, **включив в него сессионные куки**, потому что запрос уходит на тот же домен, на котором пользователь авторизован.

---

### 🛡 Почему это работает?

- **Браузер не различает “добрые” и “вредоносные” сайты**, он просто видит:
    > «Нужно отправить POST-запрос на `bank.com` — ага, у меня есть куки от `bank.com`, я их прикладываю».
- Поэтому **без CSRF-защиты** `bank.com` примет запрос как настоящий от пользователя и выполнит его.

---

### 🔒 Как защититься?

1. **CSRF-токен** в форме — токен лежит в сессии и в форме, злоумышленник не может его предугадать.
2. **Проверка Origin/Referer** (дополнительная мера).
3. **Не принимать запросы без CSRF из форм**.
